v32-arm64-test (PRERELEASE, NOT PINNED IN HYDROGEN): the first ARM64 (aarch64) golden image, for Windows-on-ARM (Snapdragon) hosts. Test artifact only; no Hydrogen build consumes it.

What it is: the same full-profile bake as v31-full (image/bake-in-distro.sh, branch arm64-golden-image), run on an arm64 ubuntu-base-24.04.5 rootfs. The OS, code-server 4.124.2, node, git, gh, python, and the Claude Code (2.1.294, linux-arm64) and Codex (linux-aarch64) extensions and their wrappers are NATIVE arm64. adom-wiki 1.7.68 is native arm64 (the registry publishes linux/arm64). Our other CLIs (adom-cli, adom-bridge, adom-vscode, adom-tts, adom-shotlog, adom-parts-search, digikey/jlcpcb/mouser) are the registry's x86-64 binaries, run transparently by QEMU 11.1.2 user-mode emulation (Debian's static qemu-x86_64, sha256-pinned; Ubuntu's QEMU 8.2 segfaults on every Rust binary) registered with binfmt_misc at boot by adom-binfmt-x86_64.service (additive, never flushes, leaves WSLInterop alone) and re-asserted every 60 s by a timer, plus the amd64 multiarch libs.

Baked on an Azure arm64 VM in systemd-nspawn (no arm64 WSL host was available). Verified by booting the released tarball under systemd-nspawn with no host binfmt entry: systemd "running", zero failed units, code-server :7380 up, /proxy/<port>/ route 200, adom-relay and adom-shotlog (both x86-64) running under QEMU, every x86-64 CLI answers --version, a post-bake `adom-wiki pkg install adom/adom-step2glb` installs and runs an x86-64 binary. NOT verified: an actual `wsl --import` on Windows-on-ARM.
